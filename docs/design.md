# 设计说明

> 这份文档回答一个问题：**这套东西为什么长成现在这样**。
> 逐条的取舍与代价在 `DECISIONS.md`（D-1 起），这里只讲主线。
>
> 数据来源、许可与出处见 `NOTICE.md`；跑起来看 `README.md`。

## 1. 一句话

一个基于 **MCP（Model Context Protocol）** 的本地工具服务：对一份示例数据库和一份公版文本库
开放 6 个工具，其中「查询数据库」这条链路允许模型自己写 SQL —— 因此**护栏、鉴权、
失败现场、数字口径**这四件事必须真的成立，而不是文档上写着成立。

它的用途是**技术验证**：证明「工具级 scope 下沉 + 三层 SQL 护栏 + 有界重写状态机 +
可复核的数字口径」是一套可迁移的工程约束，换一份数据也能照搬。

## 2. 主线：一次 `ask_database` 调用经过什么

```
调用方（MCP 客户端）
  │  tools/call  ask_database(question, token)
  ▼
server.py ── 注册表自检（实际注册的工具名 == TOOL_SCOPES 的键集合，不等就拒绝启动）
  │
  ├─ auth.guard(tool, token) ──▶ 不过就返回 err_code，永不抛异常
  │
  ▼
t2sql_core 状态机（有界重写，上限 2 次）
  │
  ├─ 1 取结构      db_tools.schema_doc()   ← 内部连接，不经 run_sql
  ├─ 2 让模型写 SQL
  ├─ 3 guardrails.check_sql()  ← 第一层：文本校验
  ├─ 4 执行        guardrails.run_select() ← 第二、三层：只读连接 + 引擎级 authorizer
  └─ 5 失败就带着失败原因回灌给模型重写；耗尽后返回**完整失败现场**
  │
  ▼
cost.py 逐次调用落账（JSONL 只追加，绝不抛异常）
```

三条 scope：`db:read`（列表 / 结构）、`db:query`（查询 / 问答）、`kb:read`（检索 / 取文）。
scope 挂在**工具**上，不挂在「用户」上 —— 换一个客户端、换一次会话，权限判定都一样。

### 2.1 为什么护栏是三层（`mcp_server/guardrails.py`）

| 层 | 手段 | 挡住的 |
|---|---|---|
| L1 | 静态文本校验：剥注释 → 拒多语句 → 必须 `SELECT`/`WITH` 开头 → 拒写/管理关键字 → 拒 `sqlite_master` → 缺 `LIMIT` 自动补、显式超限则拒 | 手写错误的 SQL、明显的越界意图 |
| L2 | `mode=ro` 的物理只读连接 | 拼接绕过 L1 的写操作 |
| L3 | `sqlite3.set_authorizer` 引擎级回调 | 前两层都没想到的写法 |

**只有 L3 是「绕过了也写不进去」。** L1 挡不住 `SEL/**/ECT` 这类变形，L2 挡不住
「换个文件再 ATTACH 过来写」。L3 在引擎回调里对写类操作、`PRAGMA`、`ATTACH`、
`sqlite_` 前缀表的读一律 `SQLITE_DENY`。
**注意**：绝不能对 `SQLITE_SELECT` 返 `DENY` —— 那会把正常查询一起拒掉。
代价是 `pragma table_info` 也被自己挡住，所以 `get_schema()` 走独立内部连接，
这一点写在 `get_schema` 的返回说明里，而不是藏在代码里。

**缺 `LIMIT` 是改写、不是拒绝**：这条规则防的是内存爆掉，不是安全。
拒绝会让状态机白白重写一轮。它在报告里单列一行，期望栏写「改写（非拒绝）」，
与「`LIMIT` 超上限 → 拒绝」并排，免得被读成漏了一条负例。

### 2.2 为什么失败现场要完整带出来

重写耗尽后返回的是 `{status: "failed", sql: 最后一次的 SQL, attempts, history: [逐次过程], error}`，
不是一个干净的 `EXHAUSTED` 错误码。这是个人技术验证项目：**失败样本本身就是产物**，
它们进台账当负例比一个好看的错误码有用。

## 3. 副线：数字是怎么被管住的

一条链路上有三个地方会「悄悄给出错数字」：评分口径、噪声带、报告措辞。
这三处都不靠自觉，各自有机械判据。

### 3.1 双口径评分（`mcp_server/eval_grading.py`）

同一批题报**两个**数：严格 `EX`（结果集逐格相等）与**投影容忍**（只看题目问的列）。
两个都报是因为它们会分开动：模型可能列选对了、值算对了，但多带了一列无关字段 ——
只看严格口径会说「它不会做」，只看容忍口径会说「它都会做」。

### 3.2 噪声带必须先量出来（`experiments/21_noise_band.py`）

同一臂（同一提示词版本）在 `temperature=0` 下**连跑两遍**，逐题比对，
翻转的题数就是噪声带。这个数由脚本实测并落盘，不是文档里的常量。
`experiments/20_pair_test.py` 读这份实测值 —— 任何版本差异**先和噪声带比**：
落在带内只写「方向，未达可判定水平」。

尺子自己也有正负控：两遍完全一样时必须量出 0，第二遍故意抖 3 题时必须正好量出 3。
量大了会把真差异盖住，量小了会把抖动写成改进 —— **两种错法都不会自己暴露**。

### 3.3 措辞纪律分两层

`eval_grading` 里有一张禁用词表。静态扫描只看**给人读的成品**
（`reports/**/*.md` + 根目录的结果文档）；程序生成的报告另由
`eval_runner.write_report()` 在**真实产物**上查一遍全文。
分两层的原因很实际：源码里必然要出现这些词（词表本身、断言它们会被抓住的测试），
一层扫会把**执行机制**当成违规，而真正的风险反而淹没在噪声里。

## 4. 验证架构：台账、闸门、负控

```
tools/check.py            闸门：按顺序跑，退出码 = 卡在第几步
  ├─ 1  python -m pytest                      单元测试（最细一层）
  ├─ 2  experiments/19_verify.py              台账：真的把每个入口脚本跑一遍
  └─ 3  experiments/25_deliverable_check.py   交付物：文档说的和仓库里的对不对得上
```

**为什么台账和闸门都要有**：读者不同。台账给「想知道细节的人」，它必须跑完全部、
把失败也列出来；闸门给「决定要不要发布的那一刻」，它只要一个数字。

### 4.1 纯逻辑必须落在 `mcp_server/` 下

`experiments/` 下的文件名以数字开头，**以数字开头的模块没法 import**。
判定逻辑若写在 `19_verify.py` 里，就只能靠「跑一遍 19、看它绿不绿」来测 ——
而这恰好是最需要被独立测的一块。所以拆成两半：

| 纯的一半（可 import、可单测） | 有副作用的一半（入口脚本） |
|---|---|
| `mcp_server/selfcheck.py` | `experiments/19_verify.py` |
| `mcp_server/verify_kit.py` | `experiments/25_deliverable_check.py` 的判定部分 |
| `mcp_server/deliverable_kit.py` | 同上 |

同一手法用了四次（另一次是 `eval_grading` / `eval_runner`）。

### 4.2 「未完成」是一个必须交证据的状态

本仓库有一批脚本需要模型凭据，而默认环境里没有。它们以退出码 5 结束，
并写下 `reports/*_NOT_RUN.md`。三件事同时成立才算「未完成」：

1. 退出码是脚本文件头声明的那一个；
2. 留下了写明卡在哪一步的 `*_NOT_RUN.md`；
3. `BLOCKERS.md` 里有一条对应的最小动作。

缺任何一条都是 FAIL。**没有落盘、没有解法的「未完成」，和「忘了跑」长得一模一样。**

### 4.3 负控：证明检查**会红**

每一项检查都配一个「往临时目录里放一样坏东西、看它红不红」的用例，
以及反方向「把坏东西拿走，它必须回到 PASS」。只测前者，一个永远返回 FAIL 的
实现也能通过；只测后者，一个永远返回 PASS 的实现也能通过。

`19_verify.py --selftest` 把这件事做成一个可重跑的入口：S1~S8 各放一种污染、
逐项报红，清掉污染后逐项报绿。

### 4.4 报告不能成为它自己报告的污染

这是本仓库踩得最深的一个坑，**同一种回路出现过三次**：

- 自检报告要写出「在哪里命中了什么」，写出来的那一刻，报告自己就带上了那个词；
  下一轮扫描在 `reports/verify.md` 里再次命中它。
- 检查项的**标题**本身也是内容：一个不巧的措辞让某条检查自己就是一处命中。
- 「命中的行」被引用进报告后，每轮还会多套一层反引号（实测长过三代）。

两种处置，按「引用是为了什么」分开：

| 情形 | 处置 |
|---|---|
| 报告只需要指出**位置** | 掩码（`selfcheck.mask_all` → `〔已隐去〕`） |
| 报告必须显示**路径或模式**才有用 | 把**生成物**排除出它自己喂的那条检查 |

并且都配了机械保证：`scan_report_carrier()` 在写盘前扫一遍即将成为报告的文本，
扫到的词**先掩码再写进报告**；`19_verify.py` 的 S9 项在渲染之后回读一遍，
把结论写进报告再重渲染，迭代到不动点。

## 5. 交付物核验：文档说的和仓库里的对不对得上

`experiments/25_deliverable_check.py`（判定在 `mcp_server/deliverable_kit.py`）查 8 条，
全部是「一个不认识这个仓库的人照着文档做，会不会被坑」：

| 项 | 查什么 |
|---|---|
| G1 | `data/` 下的数据文件与清单**双向**一致（文件在、清单里没有也算不合格） |
| G2 | 逐篇重算 sha256 与清单比；示例库另与 `NOTICE.md` 里**手写**的那一行比 |
| G3 | 语料清单里每一篇的出处都能在 `NOTICE.md` 里找到 |
| G4 | 文档里每条 `python <脚本>.py --flag` 的脚本与参数都成立 |
| G5 | README 的工具表与 `auth.TOOL_SCOPES` 双向比对 |
| G6 | README 提到的仓库内路径都存在 |
| G7 | 文档引用的 `reports/*` 存在，**或当场说明它还没生成** |
| G8 | 代码里的第三方 import 都在 `requirements.txt` 里声明 |

它第一次跑出来就抓到四行**真的会误导人**的文档（细节见 `PROGRESS.md` 阶段 5 明细）。

**这张表不能说明什么**（原文也印在报告末尾）：不判断文档写得好不好；
`SKIP` 不等于 `PASS`；G4 查的是「`--flag` 这个字符串在源码里出现过」，
不是「argparse 真的注册了这个参数」。

## 6. 边界

- **不联网也能跑**：数据随仓库分发（公版文本已随仓提交，示例库的 `.sql` 也在），
  只有「重新抓语料」这一个脚本需要网络，且它是可选的。
- **不需要模型凭据也能自检**：`pytest`、`19_verify.py`、`25_deliverable_check.py`
  三条都不调用模型。需要模型的那几项在配好凭据之前一直是 `SKIP`。
- **不写死数字**：报告里的每个数字都能指出「脚本名 + 口径」，
  没有估计值；金额在没有可引用单价时留空，**绝不用别家单价兜底、绝不填 0**。
